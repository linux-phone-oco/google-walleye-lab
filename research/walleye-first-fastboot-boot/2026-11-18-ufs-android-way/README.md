How Android brings up this exact UFS card (SK hynix H28U74301AMR fw D003, 64 GB, HS-G3 2 lanes rate B on the MSM8998 host), read from Google's published GPL wahoo kernel and the keeper's live readings, compared with our z13 path (kernel `topic/ufs-hynix-quirks` d49d54405 on v7.3). Research only: nothing built, the phone untouched. Clean room: facts, sequences and register/value lists only; no vendor source is kept in any tree. 2026-11-18, walleye-research.

## What was read where
- **Vendor source**: Google `kernel/msm`, branch `android-msm-wahoo-4.4-android11`, head `52750b8f2138c6e15cdd6c54ac8d2929ee696b95` (Google's last stock wahoo 4.4), read over gitiles (`scripts/fetch-vendor.sh`). Files: `drivers/scsi/ufs/{ufshcd,ufs-qcom,ufs_quirks}.[ch]`, `drivers/phy/phy-qcom-ufs*.{c,h}`, `arch/arm/boot/dts/qcom/msm8998*.dtsi` (the base soc, v2, pinctrl, mtp rails).
- **The running kernel is not that tree**: the phone runs LineageOS, kernel `4.4.302-g113bd1cfa6f5` (a Lineage fork with later 4.4 stable merges). Google's stock branch was read because it is the vendor sequence the stock bootloader pairs with; the Lineage fork's UFS files were NOT read, so a Lineage-only change in UFS code is not known. The live readings below are the ground truth where the two could differ.
- **Live Android** (keeper's read-only material, `../2026-11-18/`, `../2026-11-19/`): dmesg order, `debugfs` (host_regs, power_mode, query_stats), sysfs rpm/spm levels, the running fdt's ufshc and phy nodes (`dt.txt`), config.
- **Ours**: v7.3 at d49d54405 (`scripts/extract-ours.sh`), and the compiled `out-z13/msm8998-google-walleye.dtb`.
- **Not read, so not known**: what the bootloader (abl) leaves configured at hand-over (host registers, PHY state, gear, clocks); the UFS_HW_VERSION register of this host (which of the vendor's two PHY tables Android ran); the PHY registers after Android's init. Nothing about abl's hand-over is inferred here.

## Method (rerun with `scripts/run-all.sh`, shell/awk/cc/dtc only; results in `results/`)
1. `phy-tables.sh`: both QMP UFS PHY init tables as sorted "absolute offset, value, register name" lists (macros resolved by compiling the table text in a scratch dir), diffed by offset.
2. `quirks.sh`: device quirk tables and host flags of both sides as lists; which apply to THIS card (SK hynix, model string H28U74301AMR; both sides match a model by prefix).
3. `dt-props.sh`: ufshc and ufsphy node properties, live fdt vs our dtb, normalised key/value lists, diffed.
4. By hand, only the narrow paths: probe-time reset order, power-up sequence, link startup, power-mode change, the purge/flag handling.

## What Android does for this card (sequence, in words)
1. At probe (`ufshcd_init`): host full reset (the UFS_BCR block reset), then **a hardware reset pulse on the card's RST_n** (pinctrl state `dev-reset-assert` = pin `ufs_reset` driven low, then `dev-reset-deassert` high, each held 10-15 µs), then host controller enable.
2. HCE-enable pre-change: force memory config, power-up sequence = PHY reset asserted 1 ms, PHY calibration tables written, reset released, 1 ms, serdes started, wait for PCS ready (1 s limit), unipro mode select; then lane clocks on; ICE (crypto engine) initialised.
3. Link startup pre-change: unipro timers for PWM-G1 slow-auto, **RX line config enabled in the PHY**, unipro core clock cycles 150 with divider cleared, host hardware clock gating enabled, PA_Local_TX_LCC_Enable 0, and (QuniPro clock gating, host v3) all save-config-time mode bits set in PA_VS_CONFIG_REG1; post-change: auto-hibern8 clock-request bit if AH8 were supported (it is not: `auto_hibern8 support = 0`).
4. Device init, descriptors, then device quirks from the card's id: **for this card only one applies**: HOST_PA_SAVECONFIGTIME (sets bit 12 of PA_VS_CONFIG_REG1). The vendor Hynix entries with model prefixes hB8aL1/hC8aL1/hD8aL1/hC8aM1/h08aM1/hC8GL1/hC8HL1 (HS-G1-to-G3 two-step switch) do not match "H28U74301AMR".
5. Power-mode change to HS rate **B**, gear 3, 2 lanes each way (limits compiled in); live: first link "gear 1, 1 lane, SLOWAUTO" at 1.82 s, then "gear 3, 2 lanes, FAST, rate 2(B)" at 2.05 s, LUNs scanned right after.
6. Steady state: clock gating with hibern8, rpm/spm level 3 (device SLEEP, link HIBERN8), no auto-hibern8, clock scaling off at first (init writes `clkscale_enable 0`, then 1 at boot completed), PM-QoS on two CPU groups, bus bandwidth votes per gear.
7. Purge: the vendor driver never sets fPurgeEnable itself. Live query counters (read once, 42609 requests): flags set: fDeviceInit only; cleared: IDN 0x04 only; attributes written: IDN 0x03 and 0x0D; one UNMAP (discard) was issued in normal Android operation (filesystem), no purge.

### PHY table diff (offsets absolute; details in `results/phy/`)
Mainline's msm8998 entry points at the sdm845 tables. The vendor picks its rate-A table by the host's UFS_HW_VERSION: 3.0.0 or 3.1.0 (rate-B adds VCO_TUNE_MAP 0x44 in both trees: same).
- Against vendor **3.1.0** (10 differing lines): PLL_IVCO 0x0f vs ours 0x07; RX_EQU_ADAPTOR_CNTRL4 0x1d vs 0x1b (both lanes); ours writes in addition TX_RES_CODE_LANE_OFFSET_TX/RX (0x04/0x07, both lanes) and RX_MODE_00 0x59 (both lanes) that the vendor table does not; the vendor writes PHY power-down control 0x01 in the table (mainline does it in code).
- Against vendor **3.0.0** (35 differing lines): the above plus CP_CTRL_MODE0/1 0x08 vs 0x06, PLL_CCTRL_MODE0/1 0x34 vs 0x36, VCO_TUNE1_MODE0/1 0xcb/0xb2 vs 0xda/0xc1, PLL_IVCO, RESETSM_CNTRL 0x20 ours-only, and about twenty second-lane and PCS entries the 3.0.0 table lacks.
- Which one Android ran is **not known yet** (the HW version register was not read). The vendor driver names 3.0.0 as the oldest version with this PHY (its SVS2 comment); that msm8998 is 3.0.0 and sdm845 3.1.0 is only a guess from the fact that mainline's tables equal the 3.1.0 ones to within the lines above: not a reading.
- These are analog tuning values, not an erase path; they matter for link stability at HS-G3.

## The yoshino erase
Sony's downstream fix (earlier research row walleye-ufs-hazard-verdict): NO_PURGE for two Hynix models at fw D001 and for devices older than UFS 2.1, EXTEND_SYNC_LENGTH for all Hynix, PA_AvailTxDataLanes = 1. **None of the three exists in Google's vendor sequence for this card**: Android runs it at HS-G3 with two TX lanes, default sync length, and never touches purge. The mechanism of Sony's erase stays unpublished, so this does not show that our path is safe; it shows that the Sony quirks are Sony's workarounds for another phone's cards (Hynix hB8aL1/hC8aL1 D001, here H28U74301AMR D003) and that z13 carries four flags Android proves this card does not need to boot.

## Verdict (plain words)
1. **z13 does not match Android's sequence, and the four extra Hynix flags move it away from it** (one TX lane, extended sync length, a delay): they are untested on this card, and Android's two-lane link is the only proven one. Matching Android for this card means: quirk set = SAVECONFIGTIME only (keep the NO_PURGE *guard*: harmless, Android never purges), PHY tables of the vendor's version, ICE/loads/bus votes (low risk for a read-only probe), and the one thing that changes the card's state: **the RST_n pulse**.
2. **The RST_n pulse cannot be done with the current dts and pinctrl** (UFS_RESET is pin 153, outside `ngpios = 150`). It can be: widen the msm8998 tlmm gpio range as sdm845 does for its pin 150 and add `reset-gpios`, or toggle the pin group through pinctrl states as the vendor does. Either is a kernel change to be built and reviewed; neither is tried. Whether pulsing the card is *safer* than leaving abl's state is unknown: Android does it, Sony's mainline did not, and nobody has published what erased Sony's phones.
3. **Matching does not make the probe safe enough to take back to the author as it stands.** What would still be risk after matching: (a) abl's hand-over state is unread (the link may be up in HS at probe: a link startup against a card not reset); (b) the erase mechanism is unknown; (c) there is no way back from an erased bootloader (EDL: no public programmer; research walleye-edl-way-back); (d) the PHY version and our table equality are unproven.
4. **What can be proved before any try, without touching our kernel's UFS** (queued, read-only, for the keeper): on live Android with root, (i) the UFS_HW_VERSION register and the full host register file (`debugfs` host_regs shows only 0x00-0x9f; read 0xe0 and the vendor debug-regs), (ii) the PHY registers after Android's init, to compare with the table values (does 3.0.0 or 3.1.0 match the silicon), (iii) the pad state of ufs_reset. The vendor-kernel-as-instrument run (vf) can show what abl leaves only if its kernel runs without its UFS driver: a separate question, with its own bus-hang risk (an unclocked read), not proposed here.
5. **Recommended next step**: the three reads of 4 on the live Android (no risk to the bootloader), then a builder item for a matching z-image (quirk set, PHY table, reset), built and reviewed, not tried. The author's "Yes, wait" stands until then.
