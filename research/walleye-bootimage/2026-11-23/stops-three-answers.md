Three answers for each of 2026-11-23's stops (item walleye-stops-three-answers, walleye-research, no phone touched): (a) should the check exist, (b) how Android or upstream does it, (c) what let it through. Stops: stage 2 checks 18, 9, 16; stage 1 check 17 (the log line, then noload versus norecovery); the run 4 and 7 pstore reads; the UFS try 2 step 16. The stage 2 table of all 29 steps is research/walleye-bootimage/2026-11-23/stage2-checks-should-they-exist.md; this file adds what it did not cover and points to it.

## Stage 2 check 18, flags after the flash (twice: successful and retry; then unbootable)
(a) Should it exist: for the flashed slot, no. Its purpose was "the flash changed only what a flash changes". But the bootloader may reset any of the target's flags (run 5: a no-op flash of boot_a took unbootable yes to no and retry 0 to 1), and update_engine itself puts the target in unbootable first. For Android's slot and current-slot it stands (a way back, invariant I4). Purpose still stands for those two, not for the flashed slot.
(b) Android: fastboot `flash` asserts nothing of the target's flags (fastboot.cpp do_flash/flash_buf); `set_active` "clears slot-unbootable"; update_engine MarkSlotUnbootable before writing (download_action.cc l.199) and SetActiveBootSlot after verifying; boot_control HAL only exposes the bits (BootControl.cpp). Sources: aosp-fastboot-cpp-android11, aosp-update-engine-download-action, aosp-update-engine-boot-control-android, aosp-boot-hal-bootcontrol.
(c) What let it through: an expectation written from one run's printed flags (a typed stand-in), no source; the rehearsal writes nothing so never sees a flag a flash changes; the repeat audit walked a repeat of a successful flash, not of a failed boot (the state walk, item walleye-stage2-state-model-walk, is the catch).

## Stage 2 check 9 (boot_a equals the stock backup) and check 16 (the flash changes boot_a)
(a) Check 9: no as an assertion of the live content (the overwrite destroys it whatever it was); yes as "the backup is on file and hashes to its record" (I4). Check 16: keep "boot_a reads back as the image and no other boot/dtbo/vbmeta changed" (I1, I3); never require a change (flashing equal bytes changes nothing).
(b) fastboot flash reads nothing of the target before and does not read back (no read in the protocol); update_engine verifies the target hash after writing and never asks what the slot held. Sources: aosp-fastboot-cpp-android11, aosp-update-engine-fs-verifier.
(c) Both assumed the state of a first run (boot_a is stock, boot_a differs from the image). The rehearsal ran on a phone never flashed. Runs: rerun 2 (check 9), rerun 3 (check 16), rehearsal 5 (check 8's twin). A review question that catches them: "what does this assert about a state this command did not create?".

## Stage 1 check 17, the log line (run 3) then noload versus norecovery (run 4)
(a) Should it exist: yes. Its purpose: the root is the card mounted read-only without journal replay under an overlay, handed over by init (so the card is never written by the try). That purpose stands; the evidence for it is the mount itself.
(b) How the kernel does it: the ext4 option table lists both spellings for one token, `{Opt_noload, "norecovery"}` then `{Opt_noload, "noload"}`, and /proc/mounts prints the option through token2str, which returns the FIRST pattern of that token: "norecovery" (android_kernel_google_wahoo lineage-22.1 at 113bd1cfa6f5, fs/ext4/super.c l.1207-1208 and token2str l.1825-1833; mainline keeps both spellings, fs/ext4/super.c fsparam table "norecovery" and "noload"). So a check on /proc/mounts for "noload" can never pass on any ext4. For the log line: init's say() writes /dev/kmsg, and /dev was moved into the new root before the line ('handing over' after mount --move /dev), so the line never reached the kernel log (run 3); the working systems read the state (PID 1, the overlay mounts), not an announcement. Source: src-android-wahoo-kernel-ext4-super (new), and the measured run 3/4 text.
(c) What let it through: the check's stand-in MOUNTS line (rootfs_boot.rs:1184) was typed with "noload", the option as written on the command line, not as printed by a phone; no phone text was kept as the fixture. And the log-line check trusted an announcement whose own write path the init's order had cut: an expectation about the init's output that no run of the init (even in a host namespace) had printed.

## The run 4 and run 7 pstore reads (pstore as the evidence channel for slot a)
(a) Should it exist: the read, yes, as a free read from Android (nothing sent); as THE evidence channel for slot a, no. A reset by the PMIC watchdog is a hard reset: DDR is not kept, ramoops is empty (research walleye-pstore-warm-reset-how-it-stands, walleye-ml3-pstore-empty).
(b) Upstream: the ramoops doc and the openwrt report say ramoops survives a warm reboot, not a cold one (src-kernel-ramoops-doc, src-openwrt-ramoops-warm). Android: its kernel enables CONFIG_PSTORE, _CONSOLE, _PMSG, _RAM (wahoo_defconfig l.735-738) and its init mounts pstore early in `on init` (init.rc l.357-366: mount pstore, console-ramoops chmod 0440); whether anything else in Android reads it was not read here (not known yet). The boot reason string (bootreason=watchdog, src-android-boot-reason) is the other channel, and it did survive both runs. Source: aosp-init-rc-pstore (new).
(c) What let it through: the decision 2026-11-23-walleye-stage2-no-ssh-read-pstore-first ranked reading pstore first without the measured fact that the reset kind decides what pstore holds (and run 4's read came after a reboot had already overwritten the console). The host USB log (run 7) was the free channel that told more.

## The UFS try 2 step 16 (silent shell under load)
(a) Should it exist: the step (a bounded read under load, the gear read at the same time) yes; the 10 s shell read as a FAIL, no (decision 2026-11-23-walleye-ufs-silent-shell-is-a-reading made it a reading kept with its time).
(b) Android and upstream: nothing read that bears on it. A shell on a gadget (ACM/telnet) starved by a 2 GiB UFS read through the same CPU is plausible, but no source or measure says which part starves (not known yet; the cheap settle is a gear read from a second channel before the load, or the banner's own timestamps, item walleye-ufs-try-2-silent-under-load).
(c) What let it through: a timeout (10 s) chosen without a measured time for the shell's answer under load; runs 1 and 2 failed 15 s into the load after eight answered samples, and the logs held only procedure lines, not the phone's own text, so the first run could not tell silence from fault.

## Common cause across the stops
Each check asserted the value of a state the command or an earlier run changes (18, 9, 16), a text the checker never saw printed (17), or a channel's behaviour never measured (pstore, the shell under load). What would have caught them before the phone: a typed stand-in is never a fixture (a text a phone printed is), a state walk, and the rule that a check names its source (item walleye-checks-name-their-sources, which these rows feed as test cases).
